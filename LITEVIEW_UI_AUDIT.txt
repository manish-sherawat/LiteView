1. APP OVERVIEW
================================================================================

App Name       : LiteView (package: com.nexus)
Internal Name  : NexusDocsViewer
UI Framework   : Jetpack Compose (100% declarative)
DI Framework   : Hilt
Architecture   : MVVM + StateFlow + Repository pattern
Modules        : app, core, feature/dashboard, feature/reader-pdf,
                 feature/reader-text, feature/reader-office, feature/scanner
Themes         : 7 themes (System, Light, Dark, Sepia, Ocean, Forest, Sunset)
Min SDK        : Android 8+ (implied)
Target SDK     : 35 (Android 15)
PDF Engine     : MuPDF (via fitz/artifex library)

Summary: LiteView is a minimalist, multi-format document viewer (PDF, DOCX,
XLSX, TXT) with a custom design system called "Nexus". It is well-structured
with a clean separation of concerns and a thoughtfully built animation library.
The overall aesthetic leans toward a clean, content-first philosophy.

2. ARCHITECTURE & DESIGN SYSTEM
================================================================================

STRENGTHS
─────────
+ Custom design system with compositionLocal-powered tokens (NexusColors,
  NexusTypography, NexusShapes, NexusTheme). This is a best-practice approach.
+ CompositionLocal is used correctly — tokens are injected at the root level
  via NexusDocsViewerTheme() and consumed anywhere in the tree without prop-
  drilling.
+ @Immutable annotation is correctly used on data class tokens (NexusColors,
  NexusTypography, NexusShapes), enabling Compose recomposition skipping.
+ A well-defined, standalone animations library (Animations.kt) that mirrors
  Material 3 motion easing curves exactly.
+ Strong separation: core module houses design primitives, feature modules
  consume them.

WEAKNESSES
──────────
- NexusTopBar has TWO implementations in two different files:
    (a) core/ui/NexusTopBar.kt (simple, 1-param version)
    (b) core/ui/components/NexusTopBar.kt (with outerVerticalPadding, etc.)
  This creates confusion about which to use and how to extend.
- NexusSlider in NexusComponents.kt is an empty stub ("simplified slider")
  with no real implementation. If used somewhere, it would render nothing.
- Some composables still reference Material3 directly (AlertDialog,
  RadioButton, IconButton, TextButton) in PdfReaderScreen.kt, bypassing the
  custom Nexus design system. This causes visual inconsistencies when non-Nexus
  M3 widgets appear alongside Nexus-styled ones.
- NexusSearchBar in NexusComponents.kt exists alongside a custom search
  implementation in PdfReaderScreen.kt and a NexusTextField-based one in
  DashboardScreen.kt — three separate search entry styles across the app.
- NexusButton.kt in core/ui/ and NexusButton composable in NexusComponents.kt
  appear to be duplicates. Two "NexusButton" implementations with slightly
  different code exist side-by-side.

3. COLOR TOPOLOGY
================================================================================

PALETTE OVERVIEW
────────────────
  Theme       Background    Surface       Primary       Error
  ─────────── ───────────── ───────────── ───────────── ───────────
  Light       #F8F9FA       #FFFFFF       #000000       #FA5252
  Dark        #000000       #121212       #FFFFFF       #FF6B6B
  Sepia       #FBF0D9       #F2E6CD       #5D4037       #D32F2F
  Ocean       #E1F5FE       #F1F8E9       #0077B6       #D32F2F
  Forest      #E8F5E9       #F1F8E9       #2A9D8F       #D32F2F
  Sunset      #FFF3E0       #FFF8E1       #FF6B6B       #D32F2F

STRENGTHS
─────────
+ Every color slot is thoughtfully named (background, surface, surfaceVariant,
  primary, onPrimary, textPrimary, textSecondary, divider, error) matching
  semantic, not visual intent.
+ Dark theme uses true AMOLED black (#000000) as background, which is battery-
  efficient on OLED displays and visually dramatic — a good choice.
+ The Sepia theme perfectly replicates a warm parchment feel, suitable for
  reading-intensive use.
+ Color transitions between themes are animated via animateNexusColorsAsState(),
  meaning switching themes is smooth, not jarring.

WEAKNESSES / ISSUES
────────────────────
- COLOR HARDCODING — FILE-TYPE ACCENT COLORS: The document type colors (PDF red,
  DOCX blue, XLSX green, TXT purple) are hardcoded in both FileGridItem.kt and
  FileListItem.kt separately. These should be centralized, possibly in
  FileTypeIcon.kt (which already has a partial version in fileTypeStyleFor()).
  Furthermore, the colors differ between the two files:
    FileGridItem:  PDF=#C4362A, DOCX=#3B7DD8, XLSX=#2E9E5B, TXT=#7C5CBF
    FileTypeIcon:  PDF=#D32F2F, DOCX=#1976D2, XLSX=#388E3C, TXT=#616161
  These are NOT the same values, causing slightly different shades in list vs.
  grid vs. icon.

- PERMISSION STATUS INDICATOR: In SettingsScreen.kt, the "Granted" permission
  dot uses raw Color.Green, which is not a semantic token:
      .background(if (isGranted) Color.Green else NexusTheme.colors.error)
  This means on Sepia/Forest themes, an acid green dot will clash with the
  warm palette.

- OCEAN THEME INCONSISTENCY: ocean surfaceVariant is #B3E5FC (medium-light
  blue), but the surface is #F1F8E9 (light green). A surface of a different hue
  from the surface variant is intentional in some palettes but here it creates
  a noticeable visual discontinuity — green tones in content areas while the
  chrome is blue.

- SEPIA vs FOREST TEXT SECONDARY: Both themes use a grey/teal textSecondary
  (#795548 for Sepia vs. #455A64 for Forest). Neither secondary text color
  relates strongly to the primary colors of their respective themes, which
  creates desaturation in subtitle text.

- onPrimary NOT USED CONSISTENTLY: Some components use NexusTheme.colors.primary
  directly for text on colored backgrounds without checking if the background
  is sufficiently high contrast (e.g., on Light theme, primary = #000000, so
  onPrimary should be white — but some badge text in BottomNav uses raw
  Color.White regardless of theme).

- CONTRAST: The divider color in Dark theme (#333333 on #121212 surface) is
  subtle — ratio ≈ 1.4:1. This is below WCAG AA guideline for non-text
  graphical objects (3:1). Low-contrast dividers may be invisible on some
  displays.

4. TYPOGRAPHY
================================================================================

SCALE DEFINED (defaultNexusTypography)
───────────────────────────────────────
  Token    Weight       Size    Usage
  ──────── ─────────── ──────── ─────────────────────
  h1       Bold        32sp     Dashboard header
  h2       Bold        24sp     Dialog titles
  title    SemiBold    18sp     Card/list item names
  body     Normal      16sp     Paragraphs, settings
  label    Medium      14sp     Tab chips, captions
  caption  Normal      12sp     Subtitles, metadata

STRENGTHS
─────────
+ The type scale is pragmatic and well-proportioned for a document viewer.
  Hierarchy is clear.
+ All font families use FontFamily.SansSerif — consistent.
+ Typography is injected via CompositionLocal (LocalNexusTypography) and all
  Nexus components consume it through NexusTheme.typography.

WEAKNESSES / ISSUES
────────────────────
- GENERIC FONT: All text uses FontFamily.SansSerif, which maps to the system
  default sans-serif font (usually Roboto on Android). There is no custom font
  loaded. The app has a "font" resource directory under core/res/ but it only
  contains font_certs.xml (downloadable font certificate), suggesting a custom
  font was planned but never fully implemented.

- FONT WEIGHT GAPS: No "Light" or "ExtraBold" weights are defined. While
  appropriate for minimalist design, there's no display-weight token for large
  hero text (e.g., the 36sp "LiteView" title in DashboardScreen overrides h1
  inline with .copy(fontSize=36.sp), bypassing the token system).

- LINE HEIGHT / LETTER SPACING: No lineHeight or letterSpacing is defined in
  any TextStyle. For body text in the PDF Text Reader, this makes dense text
  blocks with a single-line height, harming readability.

- MIXED TEXT RENDERING: The NexusTopBar.kt uses basicMarquee() for overflowing
  titles. This is fine but not consistent — some screens truncate with
  TextOverflow.Ellipsis and others with marquee. Users experience different
  behaviors depending on which screen they're on.

- TEXT STYLE VIOLATIONS: In DashboardScreen.kt (empty state), NexusText is
  used with an emoji at 64sp, bypassing any style token:
      style = NexusTheme.typography.h1.copy(fontSize = 64.sp)
  This is an inline override rather than a properly defined display token.

5. SHAPE & GEOMETRY SYSTEM
================================================================================

DEFINED SHAPES (defaultNexusShapes)
─────────────────────────────────────
  Token   Shape                  Usage
  ─────── ────────────────────── ──────────────────────────────────
  small   RoundedCorner(12dp)   Cards, chips, settings rows
  medium  RoundedCorner(24dp)   Dialog content areas, thumbnails
  large   RoundedCorner(32dp)   Bottom sheets, cards, dialogs
  pill    RoundedCorner(50%)    Buttons, tab chips, search bars
  circle  CircleShape            Avatars, FABs, nav icons

STRENGTHS
─────────
+ The shape scale is consistent and modern. Using 12/24/32dp steps creates a
  clear visual hierarchy.
+ Pill-shaped elements (search bar, buttons, bottom nav) give the app a modern,
  friendly character.
+ The "large" 32dp radius for bottom sheets and dialogs follows Material You
  conventions.

WEAKNESSES / ISSUES
────────────────────
- SHAPE DEFAULT FALLBACK: The LocalNexusShapes staticCompositionLocalOf defaults
  all shapes to RoundedCornerShape(0.dp) — completely square. If any composable
  renders before NexusDocsViewerTheme provides a real value (e.g., in Previews
  or tests), all UI will look jagged.

- SHADOW SPOT COLOR: NexusCard uses .shadow(6.dp, ..., spotColor=Black.copy(0.08f))
  — the spotColor is always a dark shadow regardless of the current theme. On
  the dark/AMOLED theme with a black background and dark card surface, this
  shadow is invisible. A theme-aware shadow or skipping shadow on dark themes
  would be more appropriate.

- CARD SHAPE: NexusCard uses NexusTheme.shapes.large (32dp radius). This very
  large radius on a full-width list card can cause the accent color bar on the
  left side to visually "disappear" into the corner curve. A medium/small shape
  for list-oriented cards would be more appropriate.

6. ANIMATIONS
================================================================================

ANIMATION SYSTEM (core/ui/animations/Animations.kt)
─────────────────────────────────────────────────────
The app has a very well-designed, production-quality animation library that
directly maps to Material 3 motion specifications.

EASING CURVES DEFINED
─────────────────────
  EmphasizedEasing          CubicBezier(0.2, 0, 0, 1)     — spatial transitions
  EmphasizedDecelerateEasing CubicBezier(0.05, 0.7, 0.1, 1)— arriving elements
  EmphasizedAccelerateEasing CubicBezier(0.3, 0, 0.8, 0.15)— departing elements
  StandardEasing             CubicBezier(0.2, 0, 0, 1)     — subtle changes
  EaseInOutSine              CubicBezier(0.37, 0, 0.63, 1)  — shimmer loops

DURATION TOKENS DEFINED
────────────────────────
  Short1=50, Short2=100, Short3=150, Short4=200
  Medium1=250, Medium2=300, Medium3=350, Medium4=400
  Long1=450, Long2=500

SPRING TYPES DEFINED
────────────────────
  pressSpring()      — StiffnessMediumLow + DampingRatioLowBouncy
  entrySpring()      — StiffnessLow + DampingRatioNoBouncy
  selectionSpring()  — StiffnessMedium + DampingRatioMediumBouncy
  colorSpring()      — StiffnessMediumLow + DampingRatioNoBouncy
  dialogSpring()     — StiffnessMediumLow + DampingRatioLowBouncy
  navPillSpring()    — StiffnessMedium + dampingRatio=0.75f

MODIFIER EXTENSIONS
────────────────────
  springBounceClick(scaleDown=0.96f) — haptic + scale feedback on press
  fadeSlideIn(delay, offsetY=30dp)   — entrance animation (fade + slide up)
  shimmerEffect()                    — infinite shimmer for loading skeletons

STRENGTHS
─────────
+ springBounceClick is a high-quality, production-grade press animation that
  integrates haptic feedback with visual feedback. The scale-down (0.96f) is
  subtle and correct — not cartoonishly aggressive.
+ colorSpring() ensures theme transitions (via animateNexusColorsAsState) are
  smooth and physically natural rather than a linear cross-fade.
+ The animation spec intentionally mirrors Material 3 specs with proper
  citations in comments.
+ shimmerEffect() as a Modifier extension is a clean, reusable loading state
  indicator.
+ LaunchedEffect-based delay support in fadeSlideIn() allows staggered entry
  animations for list items.

WEAKNESSES / ISSUES
────────────────────
- PRESS ANIMATION BUG: In NexusBottomNavIcon (NexusBottomNav.kt), pressScale
  uses pressSpring() which has DampingRatioLowBouncy. Combined with iconScale
  using selectionSpring() (DampingRatioMediumBouncy), a selected nav icon can
  briefly appear to "fight" between scales if rapidly tapped. Two concurrent
  scale animations on the same element risk visual artifacts.

- SHIMMER ANIMATION MISSING: FileListItemShimmer.kt (4.8KB) exists in the
  dashboard module, but FileGridItem.kt and FileListItem.kt do NOT show a
  shimmer state — they load a thumbnail asynchronously via LaunchedEffect but
  show no skeleton/shimmer during loading. The shimmer modifier is defined but
  underutilized.

- STAGGER DELAY: fadeSlideIn() supports a `delay` parameter but in
  DashboardScreen.kt it's called as .fadeSlideIn() with no delay — all list
  items animate identically with no stagger. This misses an opportunity for a
  polished cascading entry effect.

- DOUBLE SCALE ANIMATION on NexusBottomNavIcon:
  The icon container Box has .scale(pressScale), AND the Image/Text inside it
  has .scale(iconScale). Composing two scale modifiers means the actual visual
  scale is pressScale * iconScale, which at pressed+selected state = 0.88 * 1.12
  ≈ 0.986 — effectively no change. The interactions likely cancel each other.

- EmphasizedEasing and StandardEasing are IDENTICAL:
  EmphasizedEasing = CubicBezier(0.2, 0, 0, 1)
  StandardEasing   = CubicBezier(0.2, 0, 0, 1)
  These two constants have the same value but different semantic names. This is
  a copy-paste error and misleads developers into thinking they behave
  differently.

7. TRANSITIONS
================================================================================

SCREEN-LEVEL TRANSITIONS
─────────────────────────
  Context                    Transition Used
  ─────────────────────────  ──────────────────────────────────────────────────
  Reader state change         fadeIn(tween 300) <> fadeOut(tween 300)
  Top bar visibility          expandVertically + fadeIn / shrinkVertically + fadeOut
  Search bar visibility       expandVertically + fadeIn / shrinkVertically + fadeOut
  Navigation container        graphicsLayer alpha via entrySpring
  Dialog entry (NexusDialog)  scaleIn(0.8f) + fadeIn / scaleOut(0.8f) + fadeOut
  File options bottom sheet   slideInVertically + fadeIn / slideOutVertically + fadeOut
  Theme change                animateColorAsState via colorSpring
  Thumbnail crossfade         Crossfade(tween 300)
  List item entry             animateItem() + fadeSlideIn()
  Starred indicator           scaleIn/scaleOut + fadeIn/fadeOut via pressSpring

STRENGTHS
─────────
+ Bottom sheets (FileOptionsDialog, ThemeSelectionDialog, ChangelogDialog) use
  slideInVertically from bottom — the correct pattern for sheet-style surfaces.
+ Dialog animations (scaleIn from 0.8f) follow Material Design "container
  transform" pattern, creating a sense of depth and emergence.
+ The reader's immersive mode toggle (top bar / bottom bar show/hide) correctly
  uses expandVertically+fadeIn for a smooth, bar-lifting effect.
+ Thumbnail Crossfade with tween(300ms) prevents jarring placeholder-to-image
  swaps.
+ animateItem() is used on LazyList items for smooth list reordering.

WEAKNESSES / ISSUES
────────────────────
- NO SHARED ELEMENT TRANSITIONS: FileListItem.kt imports
  LocalSharedTransitionScope and LocalAnimatedVisibilityScope (ExperimentalAPI),
  but they are never actually used in the composable body. SharedTransitionScope
  is set up in the navigation layer but produces no visual benefit — this is
  dead code that adds complexity without delivering value.

- NO PAGE TURN ANIMATION: When navigating between pages in horizontal PDF layout
  (LazyRow), there is no "page flip" or slide transition — just an instant
  scroll snap. For a document reader, a page-by-page horizontal transition
  (crossfade or slide) would feel more natural.

- DIALOG EXIT TRANSITION: The FileOptionsDialog exit animation uses
  slideOutVertically(targetOffsetY = { it }) but the Dialog composable is
  dismissed immediately via onDismissRequest — the exit animation may be cut
  short since the Dialog itself is removed from composition on dismiss. The
  AnimatedVisibility exit may not play fully.

- IMMERSIVE MODE TOP PADDING: In PdfReaderScreen and TextReaderScreen, the
  top/bottom padding animates via animateDpAsState without a specific spring —
  it uses the default tween. The result is that the content reflows slightly
  differently from the bar animation, causing a brief misalignment between
  the bar disappearing and the content shifting.

8. LAYOUT & SPACING
================================================================================

SPACING PATTERNS OBSERVED
──────────────────────────
  Location                  Spacing Used
  ────────────────────────  ─────────────────────────────────────────────────
  Dashboard horizontal pad  24dp
  Dashboard bottom pad      180dp (for nav bar clearance)
  Settings content padding  16dp + 120dp bottom
  Card internal padding     16dp or 24dp
  Bottom sheet drag handle  32dp wide × 4dp tall, centered
  FileListItem padding      horizontal=0dp, vertical=6dp (on outer card)
  FileGridItem padding      6dp on card, 16dp on inner content
  PDF reader content pad    top=16-90dp, bottom=16-90dp (immersive-aware)
  Settings item padding     horizontal=16dp, vertical=12dp

STRENGTHS
─────────
+ Content padding accounts for immersive mode in readers (animates between
  compact and expanded states).
+ Bottom sheet dialogs use proper bottom safe area clearance via navigationBarsPadding().
+ The dashboard has generous 24dp horizontal gutters which allow content to
  breathe.

WEAKNESSES / ISSUES
────────────────────
- NO SPACING TOKENS: Unlike Material 3 (which defines spacing tokens like
  space-4, space-8, space-16, space-24), all spacing is hardcoded. Values
  like 6dp, 12dp, 16dp, 24dp, 32dp, 48dp, 64dp, 120dp, 180dp appear scattered
  without a system. If the team decides to adjust global spacing, every file
  needs to be touched.

- INCONSISTENT CARD OUTER PADDING:
  FileGridItem: .padding(6dp) on card, content gets 16dp internal padding
  FileListItem: .padding(horizontal=0dp, vertical=6dp) on card, 16dp internal
  The grid item adds extra 6dp all-around while list adds 6dp top/bottom only.
  In grid mode, items appear slightly smaller relative to available space.

- GRID LAYOUT COLUMNS: DashboardScreen uses GridCells.Fixed(2) for grid and
  GridCells.Fixed(1) for list. There is no adaptive/fill behavior. On tablets
  or large-screen foldables, grid mode shows a 2-column layout that looks
  sparse with very wide cards. No breakpoint adaptation exists.

- DASHBOARD BOTTOM PADDING (180dp): This is hardcoded to account for the bottom
  nav bar. It should use navigationBarsPadding() + a fixed offset instead of a
  magic number, as 180dp may be wrong on devices with tall gesture navigation
  bars or landscape mode.

- SETTINGS DIVIDER INDENT: SettingsDivider() uses padding(start=68dp) to align
  with text content after a 24dp icon. This is consistent internally but
  differs from the 56dp icon-area used in the TopBar and other components.

- MISSING STATUS BAR PADDING on Dashboard: DashboardScreen starts content with
  contentPadding PaddingValues(top=48dp) — a hardcoded 48dp rather than
  statusBarsPadding() + offset. On devices with tall notches or cutouts, this
  top area could be insufficient.

CORE COMPONENTS AVAILABLE
──────────────────────────
  Component           File                    Notes
  ──────────────────  ──────────────────────  ───────────────────────────────
  NexusCard           NexusComponents.kt      Pressable, accent color, shadow
  NexusSearchBar      NexusComponents.kt      Pill search bar (underused)
  NexusButton         NexusComponents.kt      Solid / outlined variant
  NexusSwitch         NexusComponents.kt      Custom animated toggle
  NexusTabRow         NexusComponents.kt      Generic segmented control
  NexusSlider         NexusComponents.kt      STUB — empty implementation
  NexusDialog         NexusComponents.kt      Animated scale-in dialog
  NexusFloatingBottomNav NexusBottomNav.kt    Glassmorphic floating nav pill
  FileTypeIcon        FileTypeIcon.kt         Canvas-drawn file type indicator
  NexusTopBar         NexusTopBar.kt          Standard header bar
  NexusCollapsingTopBar NexusTopBar.kt        Scroll-aware collapsing header
  NexusText           NexusText.kt            Thin wrapper around Text
  NexusTextField      NexusTextField.kt       Input field
  NexusSurface        NexusSurface.kt         Elevated surface container
  NexusButton (alt)   NexusButton.kt          Duplicate of NexusComponents version

QUALITY OBSERVATIONS
─────────────────────
NexusSwitch:
  + Excellent custom implementation. Uses spring-animated thumb offset, animated
    track/thumb/border colors via colorSpring(). Feels native-quality.
  - The click area is only the 52×30dp track. No expanded touch target (48dp
    minimum recommended by accessibility guidelines).
  - DampingRatio is hardcoded inline: spring(dampingRatio=0.65f). This bypasses
    the animation token system.

NexusCard:
  + Combined clickable (long-press support), scale animation, shadow, clip,
    and optional accent color in one component.
  - shadow(6dp, shape=large) can cause performance issues if many cards are
    visible simultaneously (each shadow requires a separate compositing layer).
  - When onClick and onLongClick are both null, no interaction is registered
    but the card still renders with the same visual style, giving no affordance
    signal to the user that it's non-interactive.

NexusTopBar (collapsing variant):
  + Implements a manual scrollProgress-based collapse with blended background —
    this is a hand-crafted collapsing toolbar without using any library.
  + Large-to-compact title crossfade via opacity is smooth.
  - The blended background is a manual linear interpolation of Color components.
    This works but is fragile — it will produce incorrect results if the source
    or target colors have alpha < 1.0f.
  - The expandedContent slot is available but never used across the app.

NexusTextField:
  + Supports leading icon slot, outlined style.
  - No error state styling is defined.
  - No maxLength enforcement exposed as a parameter.
  - Keyboard type and IME action are not configurable via parameters.

FileTypeIcon:
  + Canvas-drawn file icon with a folded corner detail — a nice touch.
  - The canvas drawing uses magic coordinate constants (e.g., 14f * scaleX)
    without explanatory comments, making it hard to maintain.
  - TXT type uses a generic grey (#616161) with no visual differentiation from
    UNKNOWN type. Both use grey tones that look almost identical.

10. SCREEN-BY-SCREEN ANALYSIS
================================================================================

10.1 DASHBOARD SCREEN (DashboardScreen.kt)
──────────────────────────────────────────

Layout:
  - A single LazyVerticalGrid containing header content as a full-span item,
    then file items in 1 or 2 columns.
  - The header embeds: App title "LiteView", scanner icon, search field,
    tab row (All/Recent/Starred), sort order row, grid/list toggle.

Positives:
  + Compact, information-dense header that doesn't waste screen space.
  + Tab buttons (All/Recent/Starred) have their own springBounceClick with
    press-down animation and use the Nexus pill shape — polished.
  + Empty states use emoji icons at 64sp with descriptive subtitles — charming
    and friendly.

Issues:
  - The "LiteView" title (36sp) and scanner icon are in the same Row. On small
    screens, the icon touches the title with barely any spacing.
  - TabButton component re-declares its own pressSpring animation inline instead
    of using springBounceClick. Duplication.
  - Sort control uses raw .clickable {} for the sort toggle label, which does
    not have any visual press feedback (no ripple, no scale, no animation).
    A pressed state would improve affordance.
  - Search field uses NexusTextField (separate from NexusSearchBar component).
    The NexusSearchBar in NexusComponents.kt is never used in DashboardScreen,
    meaning a dedicated search component exists but is ignored.
  - View toggle ("Grid"/"List") button uses .clickable with no ripple or spring
    animation — inconsistent with the rest of the screen where everything has
    springBounceClick.
  - The "+" Add button (described in empty state text: "Tap + Add in the nav bar
    to import documents") implies a FAB or bottom nav item, but no such button
    is visible from the dashboard code — the storage flow is automatic.

10.2 SETTINGS SCREEN (SettingsScreen.kt)
────────────────────────────────────────

Layout:
  - LazyColumn with grouped SettingsSectionGroup cards.
  - Sections: Appearance, Reader, General, Permissions, About.

Positives:
  + Settings rows are cleanly structured with icon, title, subtitle, control
    alignment — standard iOS/Android settings pattern.
  + The theme selection uses a bottom-sheet dialog (ThemeSelectionDialog) with
    swipe-down-to-dismiss gesture (100px threshold). Modern pattern.
  + Changelog dialog uses a full-height (85%) sheet for content.
  + Update state machine is clean: Checking → Available/UpToDate/Error.

Issues:
  - The back button in SettingsScreen uses raw .clickable on an Image, not
    springBounceClick. Inconsistent press feedback vs. settings rows.
  - ChangelogDialog and ThemeSelectionDialog both use raw Dialog() with
    DialogProperties(usePlatformDefaultWidth=false). They bypass the NexusDialog
    component, losing the animated entry (scaleIn + fadeIn). They appear
    abruptly without an entry animation.
  - ThemeSelectionDialog rows use raw .clickable {} (no animation), unlike the
    rest of the settings which use springBounceClick.
  - The slider for font size / reading controls (NexusSlider) is referenced in
    imports but the implementation is empty — not rendered.
  - Permission status indicator uses Color.Green (raw, not theme-aware) for the
    granted state indicator dot.
  - The "Clear Cache" flow shows a NexusDialog. However the dialog text
    ("remove temporary files like document thumbnails and extracted text") may
    worry users — the word "extracted text" implies user data loss. Copy should
    be revised.
  - The update flow (download & install APK) uses a raw Download & Install
    without explicit progress steps visible to the user during download. The
    UpdateState.Downloading is defined but the UI just shows "Downloading..."
    text with no progress bar.

10.3 PDF READER SCREEN (PdfReaderScreen.kt — 1217 lines)
─────────────────────────────────────────────────────────

This is the most complex screen in the app.

Features:
  - Vertical or horizontal scrolling (LazyColumn / LazyRow toggle)
  - Pinch-to-zoom (custom gesture handler, up to 5x)
  - Double-tap to zoom (2.5x) with animated Animatable
  - Immersive mode (tap to toggle chrome)
  - Search with highlights (yellow overlay rectangles on pages)
  - Page rotation (90° increments)
  - Custom right-edge draggable scrollbar / page slider
  - "View settings" modal (background modes)
  - Background mode: Original, Paper (sepia matrix), Eye Comfort, Inverted
  - Share, Go-to-page, Bookmarks, Outline / TOC
  - Keep screen awake support

Positives:
  + The pinch-to-zoom implementation is fully custom, handling centroid-aware
    scaling and panning. This is technically impressive.
  + Double-tap zoom animates smoothly via Animatable with target-aware offsets
    (zooms toward tap point, not screen center).
  + The custom right-edge drag scrollbar is unique and effective for quick

  + ColorMatrix-based background modes (Original, Paper, Eye Comfort, Inverted)

  + Page indicator pill (bottom center) shows "Page X / N" with a pill chip

Issues:
  - LOADING STATE: "Loading PDF..." and "Loading page..." are plain text strings.

  - MIXED COMPONENT USAGE: The Rename dialog uses androidx.compose.material3.
    AlertDialog while the Go-to-Page dialog also uses M3 AlertDialog. This is
    inconsistent with the rest of the app using NexusDialog. M3's default dialog
    background will not match the Nexus theme colors on Sepia/Ocean/Forest
    themes.
  - ZOOM OFFSET CLAMPING: The zoom offset clamping after a gesture is applied
    using minOffsetX = -(screenWidthPxInt * scale - screenWidthPxInt). This only
    clamps in the X axis using screenWidth. The Y-axis clamping uses
    screenHeight. For pages taller than the screen (most PDFs), this means the
    user can pan the PDF off the bottom edge of the screen when zoomed in.
  - RENAME IS A TOAST: The rename action in PdfReaderScreen shows a Toast saying
    "Rename involves Storage Access Framework changes for content URIs. Basic
    rename logged: [name]" — this is a stub implementation that makes the app
    appear broken to the user.
  - SEARCH NAVIGATION DELAY: Search match navigation uses
    kotlinx.coroutines.delay(50ms) before animateScrollToItem. This hardcoded
    delay is a workaround, not a proper solution.
  - FILE SIZE LIMIT UX: The 100MB PDF limit shows an error state. But the error
    message ("Opening it might cause the app to run out of memory") places blame
    on the file rather than communicating the app's limitation.
  - BOTTOM NAV BAR + PAGE INDICATOR OVERLAP: Both the Floating Pill Nav Bar and
    the Page Indicator pill are anchored to Alignment.BottomCenter with
    padding(bottom=32dp). They will render on top of each other.

Positives:

11. NAVIGATION & BOTTOM BAR
================================================================================

BOTTOM NAV COMPONENT: NexusFloatingBottomNav
─────────────────────────────────────────────

Visual Design:
  - Pill-shaped floating nav bar with glassmorphic treatment.
  - Background: surfaceVariant at 85% opacity.
  - Blur via .blur(16dp) — this is Compose's blur modifier.
  - Border: 0.5dp divider color at 40% opacity.
  - Shadow: 10dp elevation with spotColor = Black.copy(0.12f).

Selected State Animation:
  - iconScale: 1.0 → 1.12 via selectionSpring
  - highlightSize: 0 → 24dp (expanding circle background) via selectionSpring
  - iconTint: textSecondary → primary via tween(300ms, EmphasizedDecelerateEasing)

STRENGTHS
─────────
+ The floating pill nav is visually distinctive and premium.
+ The selection indicator (expanding circular highlight behind icon) is a
  well-executed micro-animation.
+ springBounceClick is applied on each nav item for tactile press feedback.
+ The nav container fades in/out (visibility) with entrySpring — smooth.

WEAKNESSES / ISSUES
────────────────────
- BLUR IN COMPOSE: The .blur(16dp) modifier in Compose creates a software-layer
  blur, not the hardware-composited blur of modern OS APIs (like iOS UIBlurEffect
  or Android's RenderEffect on API 31+). On older devices (API <31), this blur
  may be performance-intensive or not fully hardware-accelerated.
  Additionally, Compose's blur modifier blurs child content, not the content
  underneath — so the glassmorphic effect is faked (the nav bar blurs its own
  background layer, not the content scrolling beneath it). The result is an
  opaque blurred surface rather than true frosted glass.

- BADGE COLOR: BadgeDot uses raw Color.Red, not NexusTheme.colors.error. On
  Forest/Ocean themes this will clash since the badge error color is a different
  shade of red.

- BADGE SIZE LOGIC: The badge shows "9+" when count > 9 in a 16dp circle.
  For counts 1-9, the circle is only 8dp — extremely small, barely visible.
  Standard Material Design badge is at minimum 6dp, but an 8dp badge with no
  text is too subtle and may be missed.

- LABEL-LESS NAV: Nav items show icons only (no text labels) in the selected
  state — only the icon color/scale changes. For users discovering the app,
  unlabeled icons reduce discoverability. Google's own Material You guidance
  recommends labels on navigation bars.

- NexusNormalBottomNav is defined but simply calls NexusFloatingBottomNav with
  homeStyle=HomeStyle.MINIMAL, ignoring the homeStyle parameter entirely in
  the Floating variant. The HomeStyle enum appears unused.

16. PERFORMANCE CONSIDERATIONS
================================================================================

POSITIVE PATTERNS
─────────────────
+ PDF pages are rendered on demand (LaunchedEffect per visible page) with a
  24-page LRU bitmap cache — avoids loading all pages at once.
+ Bitmaps are recycled properly in PdfReaderViewModel.onCleared() and when
  evicted from the LRU cache.
+ Render mutex (kotlinx.coroutines.sync.Mutex) prevents concurrent PDF rendering
  corruption.
+ Text extraction is done once at load time and stored in memory (pdfTextByPage),
  enabling fast in-memory search.
+ @Immutable on data class tokens enables Compose smart recomposition skipping.

POTENTIAL ISSUES
────────────────
- PDF COPY TO CACHE: Every content URI PDF is copied to a temp file in cache.
  For large PDFs (~100MB), this doubles memory/storage usage during loading.
  The 100MB limit check occurs AFTER the copy begins (checking fileSize from
  cursor, not the actual stream).

- SHARED PREFERENCES PERFORMANCE: PdfThumbnailCache and page count caching use
  SharedPreferences with synchronous read (prefs.getInt) in remember { } blocks
  during composition. SharedPreferences.getInt is fast for small stores but
  this pattern blocks the UI thread for prefs access during recomposition.

- SHADOW PERFORMANCE: Multiple NexusCard instances with shadow(6dp) each require
  a separate rendering layer. In a 2-column grid with 20+ items visible, this
  could cause frame rate drops on lower-end devices.

- TEXT EXTRACTION HTML STRIPPING: The PDF text extraction strips HTML with a
  regex: replace(Regex("<[^>]*>"), ""). This is done per page synchronously in
  a loop. For PDFs with many pages (100+), this could cause noticeable loading
  delay.

- NO PAGING / INCREMENTAL LOADING: The full list of files is loaded into
  uiState.documents at once. For users with thousands of documents, the
  LazyVerticalGrid will receive all items but only render visible ones — Compose
  handles this well, but initial scan + room query for thousands of items may
  still be slow.
